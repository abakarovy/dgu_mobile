# **Техническое задание на разработку модуля «Персонал и Администрация» для мобильного приложения и бэкенда «Колледж ДГУ»**

Данное ТЗ описывает требования к реализации закрытой части мобильного приложения (для преподавателей, сотрудников и администраторов), механизмам авторизации, управлению профилем (работа с фото) и мобильному административному функционалу.

### **1\. Ролевая модель (RBAC) и доступ**

Вход в данный модуль осуществляется через единую форму авторизации «Вход для сотрудников». Бэкенд определяет уровень доступа пользователя на основе следующих ролей:

1. **Преподаватель / Сотрудник:** Имеет доступ к личному кабинету и базовым функциям (расписание, профиль).  
2. **Администратор (Суперадмин сайта):** Дополнительно к функциям сотрудника получает доступ к управлению приемной кампанией (Мобильная админка) прямо внутри приложения.

### **2\. Требования к мобильному приложению (Frontend Mobile)**

#### **2.1. Экран авторизации персонала**

* **Интерфейс:** Форма ввода Логина (Email) и Пароля.  
* **Логика:** Запрос отправляется на единый бэкенд. При успешном входе приложение сохраняет JWT-токен и проверяет флаг роли (is\_admin). Если пользователь является администратором, в главном меню приложения появляется дополнительный раздел «Панель управления».

#### **2.2. Профиль сотрудника и модуль работы с фотографией**

В личном кабинете сотрудника отображается его ФИО, должность/роль и текущая фотография (аватар). Реализуется функционал смены фото:

* **Вызов интерфейса:** При нажатии на аватар открывается системное диалоговое окно ОС (iOS / Android).  
* **Способы получения фото:**  
  1. *Сделать снимок* (запуск нативной камеры устройства).  
  2. *Выбрать из галереи* (открытие системной галереи телефона).  
* **Редактирование (Нативный кроппер):** После выбора или создания снимка приложение **обязано вызвать встроенный (нативный) инструмент редактирования операционной системы**. Пользователь должен иметь возможность средствами ОС обрезать, повернуть и отмасштабировать фотографию под квадратный формат (соотношение сторон 1:1).  
* **Отправка на сервер:** Обрезанное финальное изображение отправляется на бэкенд методом POST в формате multipart/form-data.

#### **2.3. Функционал «Мобильной админки» (только для роли «Администратор»)**

Экран разделен на две основные вкладки:

* **Вкладка 1: Список абитуриентов (для техсекретарей и админов)**  
  * Вывод списка всех зарегистрированных в системе абитуриентов.  
  * Реализация строки быстрого «живого» поиска по ФИО.  
  * Возможность кликнуть на абитуриента для просмотра его контактных данных (Телефоны, Email).  
* **Вкладка 2: Управление статусом «На оплату»**  
  * Поле ввода числового значения: «Проходной балл для оплаты» (например: 4.35).  
  * Кнопка «Применить и уведомить».  
  * *Логика:* При нажатии отправляется запрос на бэкенд. Все абитуриенты, чей балл выше или равен указанному, переходят в статус «В списке на оплату», и им уходит Push-уведомление.

### **3\. Требования к Бэкенду (Backend API) и задачам на стороне сайта**

#### **3.1. Эндпоинт авторизации и отслеживания ролей**

* **Метод:** POST /api/v1/auth/staff  
* **Передаваемые параметры:** email, password.  
* **Ответ сервера:** Возвращает токен доступа и объект пользователя с обязательными флагами ролей:  
  JSON  
  {  
    "token": "jwt\_token\_here",  
    "user": {  
      "fio": "Иванов Иван Иванович",  
      "role": "teacher",  
      "is\_admin": true  
    }  
  }

\#\#\#\# 3.2. Эндпоинт загрузки и обработки фотографии профиля  
\*Если на стороне бэкенда сайта уже реализовано API для смены аватара, мобильный разработчик использует его. Если требуется доработка/создание нового метода на стороне бэкенда, то логика следующая:\*  
\*   \*\*Метод:\*\* \`POST /api/v1/user/avatar\`  
\*   \*\*Тип запроса:\*\* \`multipart/form-data\` (принимает файл под ключом \`avatar\`).  
\*   \*\*Валидация на бэкенде:\*\* Расширения \`.jpg\`, \`.jpeg\`, \`.png\`. Ограничение по размеру файла — до 5 Мб.  
\*   \*\*Пост-обработка сервером:\*\* Бэкенд пережимает полученное фото до разрешения (например, \`500x500 px\`) для оптимизации хранения, сохраняет файл, обновляет путь к аватару в БД сайта и возвращает мобильному приложению актуальную ссылку на картинку.

\#\#\#\# 3.3. API для мобильной админ-панели  
\*   \`GET /api/v1/admin/applicants\` — получение списка абитуриентов с возможностью фильтрации по строке поиска \`?search=ФИО\`.  
\*   \`POST /api/v1/admin/set-payment-cutoff\` — передача нового проходного балла. Сервер обновляет переменную в базе данных, инициирует смену внутренних статусов абитуриентов и запускает очередь отправки Push-уведомлений через Firebase (FCM) или аналогичный сервис.

\#\#\# 4\. План тестирования модуля (QA)

1\.  \*\*Проверка авторизации:\*\* Вход под учетной записью обычного преподавателя (экран админки должен быть скрыт) и под учетной записью администратора (экран админки должен функционировать).  
2\.  \*\*Тестирование нативного кроппера:\*\* Проверка корректности вызова редактора галереи на разных версиях Android и iOS. Убедиться, что на сервер отправляется именно измененная (обрезанная) версия фото, а не оригинал.  
3\.  \*\*Стресс-тест поиска:\*\* Проверка скорости фильтрации списка абитуриентов по ФИО при объеме базы более 1000 записей.
